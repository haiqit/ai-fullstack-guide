# 选型维度表：每个方案背后的技术账

产品岗说的「选型」，选的是业务方案，不是技术方案。但每个业务方案背后都有一笔技术账。

{% hint style="info" icon="calculator" %}
下面每张表都多一列「**技术后果**」——这是这本书跟别的产品书最不一样的地方。别只看选项，要看选项后面的账。
{% endhint %}

## 表一：自研 vs 买 SaaS vs 开源 🧩

| 判断维度   | 自己造         | 买 SaaS             | 用开源         |
| ------ | ----------- | ------------------ | ----------- |
| 适合什么   | 核心差异化、数据极敏感 | 非核心、成熟、要快          | 有一定定制需求、想省钱 |
| 代价     | 养人、长期维护、慢   | 被锁定、按量贵、定制难        | 自己运维、升级自己扛  |
| 技术后果   | 要设计完整领域模型   | 要做集成层（webhook、API） | 要读源码、要能改    |
| 什么时候该换 | 买不到合适的      | 成本超过自研             | 社区不维护了      |

判断心法：先问一句「这东西是不是我的核心竞争力」。不是，默认买；是，再问「开源能不能改到够用」，能就开源，不能才自研。

## 表二：免费版限制维度 🆓

| 限制维度 | 适合什么            | 技术后果           | 常见坑            |
| ---- | --------------- | -------------- | -------------- |
| 按功能  | 功能分层清晰          | 功能开关 + 权限校验    | 功能边界模糊，用户钻空子   |
| 按用量  | 资源型产品（存储/调用/单量） | 计量 + 配额 + 重置   | 跨周期边界、退款和撤销怎么算 |
| 按席位  | 协作型产品           | 成员数校验 + 邀请流程   | 离职、停用算不算席位     |
| 按时长  | 试用型             | 到期任务 + 提醒 + 降级 | 时区、到期瞬间的并发     |
| 混合   | 商业化比较成熟         | 上面全部           | 规则组合爆炸，测试成本翻倍  |

判断心法：限制维度必须能做到三件事——**可实时计量、可原子校验、可重置**。三项里有一项做不到，技术上迟早出 bug。

## 表三：权限模型 🔐

| 模型            | 适合什么        | 代价       | 技术后果            |
| ------------- | ----------- | -------- | --------------- |
| 固定角色（RBAC 简化） | 角色少、不常变     | 灵活度低     | 简单，一个 role 字段搞定 |
| RBAC（角色-权限）   | 角色多、权限可配    | 要维护权限表   | 中间表 + 鉴权中间件     |
| RBAC + 数据范围   | B 端多租户      | 复杂度上一个台阶 | 每个查询都要带数据范围条件   |
| ABAC（属性策略）    | 规则极灵活、合规要求高 | 难维护、难测试  | 策略引擎，得专门测试      |
| 自定义角色         | 大客户要求       | 组合爆炸     | 权限快照、版本化        |

判断心法：别一上来就 ABAC。绝大多数产品，**RBAC + 数据范围**就够了。什么时候必须上 ABAC？当「同一个人在不同条件下权限不同」变成常态的时候，比如「金额小于 1 万自己批，大于 1 万要上级批」。

## 表四：流程可配置性 ⚙️

| 选项          | 适合什么      | 代价         | 技术后果           |
| ----------- | --------- | ---------- | -------------- |
| 写死流程        | 流程稳定、客户少  | 客户差异大时不够用  | 简单，代码即流程       |
| 配置项（开关、参数）  | 差异小、组合少   | 组合一多没人测    | 配置表 + 校验       |
| 规则引擎        | 差异大、要客户自配 | 测试成本翻倍，难调试 | 要设计 DSL，要可视化配置 |
| 低代码 / 工作流引擎 | 流程本身就是产品  | 重、慢、难定制    | 引入一整个子系统       |

判断心法：配置化的代价是**测试成本指数上升**。每多一个配置项，理论上就要多测一轮组合。所以先问：这个配置，真的会有客户用不同的值吗？不会，就写死。

## 表五：历史数据是否随规则变 🕰️

| 选项         | 适合什么          | 技术后果            |
| ---------- | ------------- | --------------- |
| 随规则变（实时计算） | 规则极少变、无对账要求   | 简单，但改规则会污染历史    |
| 存规则快照      | 规则会变、有对账或合规要求 | 每个业务对象存一份规则副本   |
| 规则版本化      | 规则频繁变、要能追溯    | 规则表带版本，业务对象存版本号 |

判断心法：只要产品涉及钱、合同、对账、合规，一律选快照或版本化。这是**不可逆决策**，后期补得迁移历史数据。

## 表六：需求优先级模型 🗂️

| 模型      | 适合场景        | 不适合场景     |
| ------- | ----------- | --------- |
| RICE    | 需求多、有数据、要排序 | 早期没数据、需求少 |
| MoSCoW  | 一期范围谈判、外包   | 长期路线图     |
| Kano    | 判断功能值不值得做   | 排具体开发顺序   |
| 价值/成本矩阵 | 快速拍板        | 需要精细量化    |

判断心法：早期用 Kano 判断「做不做」，中期用 RICE 排序「先做哪个」，交付期用 MoSCoW 砍「这期做什么」。

{% hint style="success" icon="lightbulb" %}
六张表记不住没关系，记住一句话：**每个业务选择，最后都会变成某个技术上的硬约束。** 评审时多问一句「这会给技术留什么坑」，就够用了。
{% endhint %}
