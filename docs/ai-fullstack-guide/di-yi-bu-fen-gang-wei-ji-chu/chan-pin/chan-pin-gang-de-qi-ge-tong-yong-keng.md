# 产品岗的七个通用坑

按「雷埋在哪」分个类。每条都说清三件事：什么表现、什么后果、怎么防。

| # | 坑         | 一句话后果         |
| - | --------- | ------------- |
| 1 | 只定义成功路径   | 前端裸奔、后端返工     |
| 2 | 规则只存 ID   | 历史数据跟着变       |
| 3 | 把配置项当需求   | 组合没人测         |
| 4 | 计费边界没定义   | 计数出 bug、财务对不上 |
| 5 | 权限起步太简单   | 后期推倒重来        |
| 6 | 数据生命周期没定义 | 删不干净、成本失控     |
| 7 | 完成标准不可验证  | 做完了说「不是我要的」   |

## 坑一：只定义成功路径 🛤️

**表现**：PRD 里全是「用户可以……」，没有「如果失败……」「如果没有数据……」「如果没权限……」。

**后果**：前端裸奔，不知道空态长什么样；后端返工，错误码没定义；测试直接漏测。

**怎么防**：每个功能强制写出五种态——正常、空、加载、错误、边界。写不出来，需求就是不完整。

## 坑二：规则只存 ID，不存快照 🧾

**表现**：订单关联「取消规则 ID」，规则表一改，历史订单跟着变。

**后果**：对账不平、客诉、合规风险。

**怎么防**：涉及钱和合同的，业务对象里存规则快照（或者版本号）。这条是硬要求，没得商量。

## 坑三：把「配置项」当「需求」 🎛️

**表现**：产品说「这个做成可配置的，客户自己选」。

**后果**：配置组合没人测，线上出现「某个组合下页面崩了」。

**怎么防**：每个配置项问三句——谁会用不同值？有几种组合？组合谁来测？答不上来就写死。

## 坑四：计费或限制规则的边界没定义 💸

**表现**：「每月限 10 单」，但没定义：自然月还是滚动 30 天？时区按谁？退款算不算？跨月下单算哪个月？

**后果**：计数出 bug、客诉、财务对不上。

**怎么防**：任何「限制」「计费」需求，强制写清四个边界：周期定义、时区、冲正规则（退款/撤销）、并发处理。

## 坑五：权限模型起步太简单 🔐

**表现**：一期「就管理员和普通用户两种角色」，二期「每个客户要自定义角色和权限」。

**后果**：权限系统重写，所有接口加鉴权，数据迁移。

**怎么防**：一期就问「未来会不会有第三种角色、会不会要自定义」。会，就直接上 RBAC + 数据范围，别图省事。

## 坑六：数据生命周期没定义 🗑️

**表现**：只定义「怎么存」，不定义「存多久、怎么删、怎么归档」。

**后果**：数据无限膨胀、合规删除做不了、备份成本失控。

**怎么防**：每个核心表问一句「这数据存多久？过期删还是归档？用户要求删除时删哪些？」

## 坑七：需求没有可验证的完成标准 🎯

**表现**：「优化用户体验」「提升性能」「做得智能一点」。

**后果**：做完了产品说「不是我要的」，但谁也说不清「要的」是什么。

**怎么防**：每个需求必须能写成「当……时，系统应……」，而且能被测试验证。写不出来，退回产品。

{% hint style="success" icon="lightbulb" %}
七个坑说到底就三类根因：**只定义成功路径、规则不留快照、边界不定义。** 评审时盯这三件事，能挡掉大部分。
{% endhint %}
