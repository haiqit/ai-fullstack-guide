# 选型表：框架、数据请求、状态、样式

前端选型七层，每层一张表，都带「技术后果」和「什么时候该换」。

## 表一：框架与渲染模式 🏗️

| 选项                  | 适合什么           | 代价           | 技术后果                | 什么时候该换        |
| ------------------- | -------------- | ------------ | ------------------- | ------------- |
| Next.js（App Router） | 要 SEO、要首屏、全栈一体 | 概念多、SSR 运维成本 | 部署要 Node 服务、要处理 RSC | 纯后台可换 Vite    |
| Vite + React SPA    | 后台、内部工具、无 SEO  | 首屏和 SEO 弱    | 纯静态托管，运维简单          | 要 SEO 时换 Next |
| Nuxt（Vue）           | Vue 生态、要 SSR   | 生态比 Next 小   | 同 Next              | —             |
| Remix               | 重表单、重数据流       | 生态小          | 同 Next              | —             |
| 纯静态（Astro 等）        | 内容站、文档         | 交互弱          | 极简托管                | 要重交互时换        |

**判断心法**：先答「选型三问」（SEO、首屏、重交互）。后台 / 内部工具默认 Vite SPA，别上 SSR；要 SEO 的 C 端默认 Next / Nuxt。

再加一条：选主流框架，AI 生成质量高。Next 和 Vite + React 是 AI 生成质量最好的两个。

## 表二：数据请求方案 🌐

| 选项                        | 适合什么        | 代价               | 技术后果            |
| ------------------------- | ----------- | ---------------- | --------------- |
| RSC 里直接取（Next App Router） | 以读为主、SEO 页  | 交互刷新难            | 服务端取数，客户端要刷新得另配 |
| TanStack Query            | 重交互、多页面共享数据 | 要学缓存模型           | 客户端缓存、失效、重试     |
| SWR                       | 简单场景        | 功能比 Query 少      | 轻量缓存            |
| 手写 fetch + useEffect      | 极简、一次性      | 缓存 / 竞态 / 重试全自己写 | 容易出 bug         |
| GraphQL 客户端               | 后端是 GraphQL | 学习成本             | 按需取数            |

**判断心法**：有重交互 → TanStack Query；以读为主且用 Next → RSC 直取 + 局部 Query；极简项目 → SWR。

{% hint style="warning" %}
别手写 fetch + useEffect 管缓存，那是自己造轮子。
{% endhint %}

## 表三：状态管理 🗄️

| 选项             | 适合什么       | 代价        |
| -------------- | ---------- | --------- |
| 本地 state       | 组件内        | 跨组件要提升    |
| Context        | 跨层级、变化不频繁  | 频繁变化全量重渲染 |
| Zustand        | 轻量全局、简单    | 复杂逻辑要自己组织 |
| Redux Toolkit  | 复杂全局、要调试工具 | 重、样板代码多   |
| Jotai / Valtio | 原子化状态      | 学习成本      |
| URL 状态         | 可分享、可刷新    | 复杂状态不适合   |

**判断心法**：先问「是服务端数据吗」——是 → 请求库，不进 store。剩下按作用域从小到大选，能本地不全局。

## 表四：样式方案 🎨

| 选项                | 适合什么          | 代价             | 技术后果           |
| ----------------- | ------------- | -------------- | -------------- |
| Tailwind          | 配 shadcn、快速开发 | 类名长、要学         | 构建时生成 CSS，体积可控 |
| CSS Modules       | 组件级样式、传统      | 要写 CSS         | 作用域隔离          |
| CSS-in-JS（styled） | 动态样式          | 运行时成本、RSC 兼容问题 | 有性能开销          |
| 原生 CSS 变量 + 原子类   | 极简、要 token    | 要自己组织          | 轻量             |
| AntD / MUI 自带样式   | 用其组件库         | 定制要覆盖          | 和组件库绑定         |

**判断心法**：用 shadcn → Tailwind；用 AntD → 它自带方案；要极致性能 → 避免运行时 CSS-in-JS（尤其 RSC 下）。

## 表五：构建工具 📦

| 选项        | 适合什么             | 代价            |
| --------- | ---------------- | ------------- |
| Vite      | 大多数项目、开发快        | 生态比 Webpack 新 |
| Webpack   | 老项目、复杂定制         | 慢、配置复杂        |
| Turbopack | Next 项目          | 还在成熟中         |
| Rspack    | 要 Webpack 兼容 + 快 | 新，生态在建        |

**判断心法**：新项目默认 Vite（或 Next 自带），别自己配 Webpack。构建工具是可逆决策，别在这纠结。

## 表六：测试策略 🧪

| 层级                    | 测什么        | 成本 | 建议          |
| --------------------- | ---------- | -- | ----------- |
| 单元测试（Vitest）          | 工具函数、hooks | 低  | 核心逻辑测       |
| 组件测试（Testing Library） | 组件行为       | 中  | 关键组件测       |
| E2E（Playwright）       | 核心用户路径     | 高  | 只测 3–5 条主路径 |
| 视觉回归                  | UI 变化      | 中高 | 有设计系统再上     |

**判断心法**：E2E 只测核心路径（登录、支付、主流程），别追求覆盖率。测试是「改代码的底气」，不是 KPI。

## 表七：部署模式 🚀

| 选项           | 适合什么        | 代价        | 技术后果       |
| ------------ | ----------- | --------- | ---------- |
| 静态托管（CDN）    | SPA / SSG   | 无服务端逻辑    | 运维几乎为零     |
| Node 服务（SSR） | Next / Nuxt | 要运维、要扩容   | 要监控、要冷启动处理 |
| 边缘渲染         | 全球用户、要快     | 受限运行时     | 要适配边缘环境    |
| Serverless   | 流量波动、省运维    | 冷启动、长任务受限 | 要处理冷启动     |

**判断心法**：能静态就静态。SSR 只在「要 SEO + 要首屏」时才上，上了就要按后端标准运维它（监控、容量、回滚）。
