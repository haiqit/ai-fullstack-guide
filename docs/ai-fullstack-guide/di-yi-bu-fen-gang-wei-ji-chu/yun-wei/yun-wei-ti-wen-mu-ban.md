# 提问模板：发布、观测、验收

这些模板用在三个场合：定部署方案、设计监控告警、验收 AI 写出来的部署配置。

| 什么时候用        | 用哪个      |
| ------------ | -------- |
| 要定部署形态       | 模板一      |
| 要定监控告警       | 模板二      |
| 要定发布方式和回滚    | 模板三      |
| 要定备份灾备       | 模板四      |
| 想做一次安全基线检查   | 模板五      |
| 验收 AI 写的部署配置 | 模板六（最常用） |

## 模板一：部署形态选型

> 【背景】服务【数量 / 类型】，团队【人数】，流量【量级 / 波动】，有无长任务【有 / 无】，预算【多少】。 【约束】运维能力【有 / 无】，不能上【K8s / Serverless】，合规要求【有 / 无】。 【取舍】请对比四种方案（PaaS / 容器 + 托管编排 / K8s / Serverless），分别说明：适合什么阶段、运维成本、扩展性、冷启动 / 长任务限制、典型坑、什么信号出现时该升级。 【验收】给出推荐 + 部署拓扑 + 运维要做的最小清单（监控 / 回滚 / 备份）。

## 模板二：监控告警设计

> 【背景】服务【描述】，关键业务指标有【列出】，团队【人数】，on-call【有 / 无】。 【约束】已有【监控系统】，预算【多少】。 【取舍】请设计最小可用的监控告警：列 5 个必监控指标（含业务指标）、每个的告警阈值怎么定、告警分级策略、收敛规则、故障排查顺序。 【验收】给出「后端埋什么、运维接什么」的边界清单 + 每条告警对应的行动。

## 模板三：发布与回滚方案

> 【背景】服务【描述】，发布频率【多少】，数据库迁移【有 / 无】，团队【人数】。 【约束】不能停机【能 / 不能】，回滚要求【多快】。 【取舍】请对比三种发布策略（滚动 / 蓝绿 / 金丝雀），分别说明：适合什么、回滚速度、资源成本、数据库迁移怎么兼容。 【验收】给出推荐 + 一键回滚方案 + 数据库迁移向前兼容检查清单。

## 模板四：备份与灾备设计

> 【背景】数据【类型 / 量级】，业务重要性【高 / 中 / 低】，RTO【多少】、RPO【多少】。 【约束】预算【多少】，不能跨区【能 / 不能】。 【取舍】请设计备份方案：备份频率、保留期、存储位置、恢复演练频率、跨区灾备要不要做。 【验收】给出恢复演练步骤 + 怎么验证备份可用。

## 模板五：安全基线检查

> 【背景】服务【描述】，对外暴露【有 / 无】，用户数据【敏感度】。 【约束】合规要求【有 / 无】，预算【多少】。 【取舍】请列出最小安全基线：密钥管理、依赖扫描、镜像扫描、HTTPS / CSP、最小权限、审计日志、防 DDoS。 【验收】给出「现在必须做」和「规模到了再做」的分级清单。

## 模板六：AI 生成部署配置的验收 ⭐

> 你生成的部署配置（Dockerfile / K8s YAML / CI 配置），请按以下标准自查并列出不达标处： ① 密钥有没有硬编码？ ② 有没有健康检查（liveness / readiness）？ ③ 资源限制（CPU / 内存）设了吗？ ④ 日志是结构化的吗？带 trace\_id 吗？ ⑤ 有没有回滚方案？ ⑥ 镜像是最小化的吗（非 root、多阶段构建）？ 不达标的给修改方案。然后我按这个清单验收。

{% hint style="info" %}
模板六最常用。AI 写的 Dockerfile 和 K8s YAML 一眼看着都对，但六条里总有一两条会踩——尤其是硬编码密钥和非 root。**验收不是挑刺，是上线前的最后一道闸。**
{% endhint %}
