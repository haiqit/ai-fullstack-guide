# 运维不是「把服务跑起来」

后端看运维，最容易归成一句「部署上线、出问题重启」。于是态度变成：我会 Docker、会敲几条命令，运维差不多就学会了。

差得远。部署只是入场券，运维的内核是**稳定性工程**：让服务持续可靠地跑，坏了能快速定位和恢复，还得让成本可控。

## 服务跑得好好的，突然就慢了 🐌

你第一反应是「代码有问题」。翻代码，没毛病。

真实原因可能是这些：

| 看起来像「代码 bug」 | 其实是谁的问题      |
| ------------ | ------------ |
| 数据库连接数打满     | 资源规划和连接池配置   |
| 某个依赖变慢       | 超时和降级没做      |
| 磁盘写满了        | 日志没设保留期      |
| 内存一路涨        | 泄漏 + 没设限制    |
| 证书过期         | 没人盯有效期       |
| DNS 解析慢      | DNS 缓存和解析器配置 |

六个里没有一个在代码里。而且这类问题在生产环境里，比代码 bug 更常见。

## 想回滚，发现没有回滚方案 ⏮️

发布新版本，上线出事。你想回滚——没有回滚方案，只能往前修。

> 没有回滚方案的发布，等于赌博。赌的是这次不会出事。

这是运维能力缺失最典型的代价。

## 作为全栈，你多出来的那个视角 🔍

专职运维做不了一件你天生就能做的事：**从写代码那一刻起就考虑可运维性。**

| 你写代码时 | 顺手就把运维前提做好了         |
| ----- | ------------------- |
| 写接口   | 健康检查、业务指标、结构化日志一次埋好 |
| 设计调用  | 超时、重试、降级想清楚         |
| 定架构   | 部署形态和回滚方案一起定        |

这些事纯运维推不动——他们改不了你的代码。纯后端也想不起来——他们不管线上。只有全栈能一次做对。

{% hint style="info" %}
这就是第 6 章那句「谁写的代码谁埋」，在运维视角的续写。埋什么、接什么，是在你写代码时就要划清的边界，不是上线后补的。
{% endhint %}

## 这一章讲三件事 🎯

1. **运维岗真正在决策什么** —— 三个层次，能力要求完全不同
2. **每个决策点有哪些选项、代价是什么** —— 八张选型维度表，每张带「什么时候该升级」
3. **每个运维决策会给后端、前端、产品埋什么坑** —— 全栈视角最值钱的部分

## 一句话 ⭐

{% hint style="success" %}
你不是要当专职 SRE。你是要**能独立扛住一个小团队、一个独立产品的运维**，并且知道什么时候该找专业的人、该补哪块。
{% endhint %}
