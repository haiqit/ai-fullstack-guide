# 运维岗的十二个通用坑

每条都说清三件事：什么表现、什么后果、怎么防。

| #  | 坑            | 一句话         |
| -- | ------------ | ----------- |
| 一  | 密钥硬编码        | 一次泄露全完      |
| 二  | 发布没有回滚方案     | 出事只能硬扛      |
| 三  | 只监控 CPU / 内存 | 用户感知的故障发现不了 |
| 四  | 告警疲劳         | 真故障被淹没      |
| 五  | 备份没验证过恢复     | 真出事发现备份是坏的  |
| 六  | 环境不一致        | 「本地是好的」变成常态 |
| 七  | 所有人都能上生产     | 误操作、安全事故    |
| 八  | 没有 SLO       | 稳定性靠感觉      |
| 九  | 日志全量存        | 存储成本爆炸      |
| 十  | SSR 服务当静态文件  | 挂了整站打不开     |
| 十一 | 过早自建全套基础设施   | 运维成本比业务还高   |
| 十二 | 无灾备、单点故障     | 一次故障全挂      |

## 坑一：密钥硬编码 🔑

**表现**：密钥写进代码、Dockerfile、环境变量文件，还提交进了仓库。

**后果**：一次泄露全完，不可逆。

**怎么防**：密钥服务 + 提交前扫描 + 轮换机制。三道一起上。

## 坑二：发布没有回滚方案 ⏮️

**表现**：上线靠「往前修」，回滚从来没测过。

**后果**：出事只能硬扛。

**怎么防**：每次发布都有回滚方案，且演练过。数据库迁移向前兼容——旧代码能跑新库。

## 坑三：只监控 CPU / 内存 📊

**表现**：监控大盘只有系统指标，没有业务指标。

**后果**：用户感知的故障（订单失败、支付失败）发现不了。

**怎么防**：加业务指标——成功率、延迟、关键操作失败率。

## 坑四：告警疲劳 🔔

**表现**：告警群天天刷屏，最后没人看。

**后果**：真故障被淹没。

**怎么防**：分级 + 收敛 + 可行动。每条告警问「该做什么」，答不上来删掉。

## 坑五：备份没验证过恢复 💾

**表现**：备份天天跑，但从没恢复过。

**后果**：真出事，发现备份是坏的。

**怎么防**：定期做恢复演练，记录 RTO / RPO。

## 坑六：环境不一致 🖥️

**表现**：本地、测试、生产的配置和依赖版本都不一样。

**后果**：「本地是好的」变成常态，预发测不出问题。

**怎么防**：容器化 + IaC + 配置管理。

## 坑七：所有人都能上生产 🔓

**表现**：权限没最小化，谁都能改生产。

**后果**：误操作、安全事故。

**怎么防**：最小权限 + 审计日志 + 堡垒机。

## 坑八：没有 SLO，稳定性靠感觉 🎯

**表现**：「感觉挺稳的」，没有指标定义。

**后果**：出问题靠吵架，扩容靠拍脑袋。

**怎么防**：定 SLI / SLO，用错误预算指导发布节奏。

## 坑九：日志全量存 📝

**表现**：所有日志永久保存。

**后果**：存储成本爆炸。

**怎么防**：分级保留（错误长期、info 短期）+ 采样 + 归档。

## 坑十：SSR 服务当静态文件 🖥️

**表现**：SSR 服务没监控、没扩容、没回滚。

**后果**：挂了，整个前端打不开。

**怎么防**：SSR 按后端标准运维——健康检查、资源限制、回滚方案一样不少。

## 坑十一：过早自建全套基础设施 🧱

**表现**：小团队自建 K8s + Prometheus + ELK + Vault。

**后果**：运维成本比业务还高。

**怎么防**：早期用托管服务，规模到了再自建。

## 坑十二：无灾备、单点故障 🌊

**表现**：数据库一个实例、应用跑在一个区、网关只有一台。

**后果**：一次故障全挂。

**怎么防**：按业务重要性做多副本 / 跨区，明确 RTO / RPO。

{% hint style="success" %}
十二个坑，根子大多落在三处：**密钥没管住、发布没法退、观测没做全。** 每次发布前先问这三样，能挡掉一半事故。
{% endhint %}
