# 后端岗的八个模块

这八个模块是后端所有语言共通的决策域。每个模块分两块讲：**知识内核**（这层到底在决定什么）和**全栈视角为什么必须懂**（它会变成谁的约束）。

```mermaid
flowchart LR
    M1["🏢 多租户隔离"] --> M2["⚡ 并发正确性"]
    M2 --> M3["🔁 幂等"]
    M3 --> M4["🧩 状态机"]
    M4 --> M5["🗄️ 缓存一致性"]
    M5 --> M6["📬 队列异步"]
    M6 --> M7["🔭 可观测性"]
    M7 --> M8["📦 部署架构"]
```

## 模块一：多租户隔离——SaaS 的第一个决策 🏢

### 知识内核

一个系统服务多个客户，数据要互相分开。三种隔离方式，隔离强度和成本正好相反：

| 方式                      | 隔离强度     | 成本              | 适合什么            |
| ----------------------- | -------- | --------------- | --------------- |
| 独立库（每租户一个库）             | 最强       | 最高（运维、迁移、备份都翻倍） | 客户少、数据极敏感、合规要求高 |
| 独立 schema（同库不同 schema）  | 强        | 中高              | 中等客户数、要强隔离      |
| 共享表 + `tenant_id`（行级隔离） | 弱（靠代码保证） | 最低              | 客户多、SaaS 主流选择   |

共享表 + `tenant_id` 是大多数 SaaS 的选择，但它有一个致命风险：**任何一个查询忘了带 `tenant_id`，就是数据泄露。** 所以必须配两样东西：

* **行级安全（RLS）**：数据库层面强制过滤。Postgres 原生支持，MySQL 要在应用层兜底。
* **强制约定 + 自动化检查**：ORM 层统一注入租户条件，代码审查和测试覆盖。

### 全栈视角为什么必须懂

多租户是产品决策和技术决策的交汇点：

* 产品定「独立库还是共享表」，**直接影响定价**——独立库成本高，售价得覆盖得住。
* 产品定「客户能不能导出全部数据、能不能要求物理删除」，**直接决定隔离方式**。
* 前端的「租户切换」「多租户后台」，要求接口支持「当前租户」的上下文传递。

{% hint style="warning" %}
多租户不只是「数据隔离」。还包括**配置隔离**（每个租户有自己的主题、规则、限额）、**资源隔离**（一个大客户不能拖垮其他客户）、**计费隔离**。这三样架构上都要预留，后期补很痛。
{% endhint %}

## 模块二：并发正确性——不是「查一下再插」 ⚡

### 知识内核

并发问题不是查询问题，是**原子性问题**。两个人同时抢最后一个资源，靠「先查再插」必然出错——查和插之间有一个窗口。

| 武器                       | 原理      | 适合什么               | 代价         |
| ------------------------ | ------- | ------------------ | ---------- |
| 唯一约束 / 唯一索引              | 数据库强制唯一 | 天然唯一的场景（如同一员工同一时段） | 冲突时抛异常，要处理 |
| 悲观锁（`SELECT FOR UPDATE`） | 锁住行，别人等 | 冲突频繁、要强一致          | 锁等待、死锁风险   |
| 乐观锁（版本号）                 | 更新时校验版本 | 冲突少、读多写少           | 冲突要重试      |
| 分布式锁（Redis 等）            | 跨进程互斥   | 跨服务、跨库             | 锁失效、脑裂，要处理 |

**判断心法**：能用数据库约束解决的，优先用数据库（唯一索引最可靠）；数据库搞不定的（跨服务、复杂条件），才上分布式锁。「先查再插」永远不是方案，它只是把并发问题推迟到线上。

### 全栈视角为什么必须懂

预约、抢单、秒杀、支付，全是并发场景：

* 产品的「时段冲突处理」、前端的「防重复提交」，根子都在后端并发设计。
* 前端的**乐观更新**依赖后端的幂等和版本校验。后端没做，前端乐观更新就是定时炸弹。
* 运维的容量规划，要考虑并发峰值。

## 模块三：幂等——「同一请求来多次」的本质 🔁

### 知识内核

幂等就是「同一个操作执行多次，结果和执行一次一样」。它出现在四种场景，本质相同：

| 场景     | 怎么来的            |
| ------ | --------------- |
| 用户重复点击 | 提交按钮点了两次        |
| 支付回调重发 | 支付平台没收到你的确认，会重发 |
| 消息重投   | 队列投递失败后重试       |
| 网络超时重试 | 客户端没收到响应，重试     |

| 实现                   | 原理                | 适合什么           |
| -------------------- | ----------------- | -------------- |
| 幂等键（idempotency key） | 客户端生成唯一键，服务端记录已处理 | 写操作通用方案        |
| 唯一约束                 | 数据库强制唯一           | 天然唯一的业务（订单号）   |
| 状态机校验                | 只允许合法状态转换         | 有状态流转的业务（订单状态） |

### 全栈视角为什么必须懂

幂等是前后端契约的一部分：

* 前端的「防重复提交」和重试，依赖后端幂等键。
* 产品的「支付回调」「消息通知」，依赖后端幂等。
* 运维的重试策略，依赖后端幂等才不会重复执行。

{% hint style="danger" %}
支付回调必须按这个顺序：**先落原始事件 → 按事件 ID 去重 → 最后才改业务状态。** 很多人「收到回调就改状态」，一重投就是重复发货、重复扣款。
{% endhint %}

## 模块四：状态机与业务正确性——把流程写成代码 🧩

### 知识内核

任何有生命周期的业务对象（订单、任务、审批、订阅、工单），都该显式建模成状态机：

1. **有哪些状态**：枚举出来，不要散落在代码里
2. **哪些转换合法**：白名单，不是黑名单
3. **转换需要什么条件**：权限、金额、时间、外部事件
4. **哪些转换不可逆**：取消后不能恢复、支付后不能退回未支付

好处很直接：业务规则集中在一处，可测试、可审计、可快照。

### 全栈视角为什么必须懂

* 产品画的流程，本质就是状态机。产品画不清的，后端要能补出来。
* 前端的页面状态、按钮可用性，依赖后端给出的状态。
* 运维排查故障，第一句就要问「现在在哪个状态、能不能回退」。

{% hint style="warning" %}
状态变更**必须留快照或事件日志**。只存当前状态的话，改规则就会污染历史——这正是产品线里反复强调的那个坑。
{% endhint %}

## 模块五：缓存与一致性——不是「加个 Redis」 🗄️

### 知识内核

缓存不是「加个 Redis 就快」，它带来三个新问题：

| 问题   | 表现                 | 解法              |
| ---- | ------------------ | --------------- |
| 缓存穿透 | 查不存在的数据，每次都打库      | 布隆过滤器、空值缓存      |
| 缓存击穿 | 热点 key 过期，大量请求同时打库 | 互斥锁、永不过期 + 异步更新 |
| 缓存雪崩 | 大量 key 同时过期，库被打垮   | 过期时间加随机、多级缓存    |

还有一个最经典的问题：先更新库还是先删缓存？

| 策略               | 问题        | 适合什么              |
| ---------------- | --------- | ----------------- |
| 先更新库，再删缓存        | 删缓存失败会不一致 | 大多数场景（配重试 / 延迟双删） |
| 先删缓存，再更新库        | 并发读会回填旧值  | 少用                |
| 更新库 + 删缓存 + 延迟双删 | 缓解不一致     | 一致性要求高            |
| 只更新库，缓存靠过期       | 短期不一致     | 一致性要求低            |

### 全栈视角为什么必须懂

* 产品对「数据实时性」的要求，决定要不要缓存、缓存多久。
* 前端的「服务端状态缓存」和后端缓存是两层，要配合，不能互相甩锅。
* 运维算容量时，缓存能省多少库压力，得算清楚。

{% hint style="warning" %}
缓存加早了 = 多一个 bug 源。**读多写少、一致性容忍度高**，才值得加；否则先优化查询和索引。
{% endhint %}

## 模块六：队列与异步——长任务、重试、削峰 📬

### 知识内核

队列解决四类问题：

| 目的     | 例子                |
| ------ | ----------------- |
| 长任务异步化 | 导出、生成报表、发邮件，不阻塞请求 |
| 重试     | 失败自动重试（前提是幂等）     |
| 削峰     | 高峰时排队，保护下游        |
| 解耦     | 服务间通过消息通信，而不是直接调用 |

三个关键设计：

* **重试策略**：几次、间隔、退避（指数退避）、死信队列
* **幂等**：消费者必须幂等，否则重投就重复执行
* **可见性超时**：消息被消费但没确认，多久后重新投递

### 全栈视角为什么必须懂

* 产品的「消息通知」「导入导出」依赖队列。
* 前端的「异步任务进度」依赖后端提供任务状态查询。
* 运维要监控队列积压和死信数量。

{% hint style="info" %}
队列不是「有了就好」，它带来**最终一致性**——用户操作后不是立即生效。前端要能显示「处理中」。产品和 UI 不定义这个状态，用户就会觉得「点了没反应」。
{% endhint %}

## 模块七：可观测性——「谁写的代码谁埋点」 🔭

### 知识内核

三件套，各回答一个问题：

| 工具         | 回答什么                  | 后端要做什么               |
| ---------- | --------------------- | -------------------- |
| 指标 Metrics | 系统健康吗（QPS、延迟、错误率、饱和度） | 暴露关键指标，**业务指标也要**    |
| 日志 Logs    | 发生了什么                 | 结构化、可检索、带 `trace_id` |
| 链路 Traces  | 请求经过了哪些服务、哪一步慢        | 埋 trace，跨服务透传        |

{% hint style="success" %}
原则：**谁写的代码谁负责可观测性。** 后端埋点、给健康检查、定义关键指标（不只是 CPU / 内存，还有订单成功率、支付失败率这类业务指标）。运维负责接进监控体系，不负责替你想「该监控什么」。
{% endhint %}

### 全栈视角为什么必须懂

这是后端和运维的边界，也是最容易扯皮的地方。后端觉得「监控是运维的事」，运维觉得「我不知道你的业务该监控什么」。

全栈的人要主动说清楚：**我负责埋什么，运维负责接什么。**

## 模块八：部署架构——单体、模块化单体、微服务、Serverless 📦

### 知识内核

| 架构         | 适合什么       | 代价          |
| ---------- | ---------- | ----------- |
| 单体         | 小团队、早期产品   | 耦合、扩展难      |
| 模块化单体      | 中小团队、要清晰边界 | 要自律（守住模块边界） |
| 微服务        | 大团队、独立扩展   | 运维复杂、分布式问题  |
| Serverless | 流量波动、省运维   | 冷启动、长任务受限   |

**判断心法**：默认单体或模块化单体。微服务的代价是「分布式系统的所有问题」（网络、一致性、链路、部署），小团队养不起。什么时候该拆？当**某个模块要独立扩展、独立部署、独立团队**时。

### 全栈视角为什么必须懂

这个决策同时影响前端（SSR 部署在哪）、运维和成本。后端选架构不能只看技术，要看团队规模、运维能力、业务阶段。
