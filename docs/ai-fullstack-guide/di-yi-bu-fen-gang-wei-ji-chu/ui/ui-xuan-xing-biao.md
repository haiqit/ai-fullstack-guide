# 选型表：设计系统、主题、交互

UI 层的选型，选的是设计系统、组件、token 策略、交互模式。每张表都带「技术后果」和「什么信号该换」。

## 表一：设计系统 / 组件库 🧱

| 选项                   | 适合什么         | 代价                 | 技术后果                        | 什么时候该换          |
| -------------------- | ------------ | ------------------ | --------------------------- | --------------- |
| 完全自研                 | 品牌独特性强、有专职设计 | 慢、贵、要维护            | token + 组件全自己写，工作量大         | 基本不换            |
| Tailwind + shadcn/ui | 要好看、要独特、团队小  | 要自己拼组件、要懂 Tailwind | 组件代码在你仓库里，可改；token 用 CSS 变量 | 团队变大、要统一规范时考虑升级 |
| Ant Design           | B 端后台、表单多、要快 | 「一眼 AntD」、定制成本高    | 开箱即用、表单生态强、定制要覆盖样式          | 品牌要求高、或做 C 端产品  |
| MUI                  | React 生态、组件全 | 重、定制要学它的方式         | 主题系统强、包体积大                  | 追求轻量时           |
| 买商业设计系统              | 企业级、要支持      | 贵、可能锁定             | 集成成本、升级受制于厂商                | 预算不够时           |

判断心法：先问三个问题——① B 端还是 C 端？B 端表单多 → AntD 类；C 端要独特 → shadcn 类。② 团队有没有设计能力？没有 → 用现成；有 → 自研或 shadcn。③ 要不要品牌定制？要 → token 必须先行，组件库选可定制度高的。

再加一条 AI 时代的判断：**选主流组件库，AI 生成质量高。** 冷门库 AI 生成质量差，你「能改」的成本反而更高。

## 表二：色彩与主题策略 🎨

| 选项             | 适合什么         | 代价           | 技术后果     |
| -------------- | ------------ | ------------ | -------- |
| 硬编码颜色          | 一次性页面、原型     | 暗色 / 换肤全量返工  | 颜色散落各处   |
| CSS 变量（token）  | 几乎所有正式产品     | 前期要定义一套      | 主题切换只换变量 |
| 主题系统（多套 token） | 多品牌、多客户 SaaS | 要设计 token 映射 | 运行时切换主题  |
| 动态主题（用户自定义）    | 极少（如建站工具）    | 极复杂          | 要存用户主题配置 |

判断心法：正式产品一律 token 先行，没有例外。暗色模式、品牌定制、无障碍对比度，都依赖 token。什么时候上多套 token？当一个产品卖给多个客户、每个客户要自己品牌时。

## 表三：图标与字体 🔤

| 决策点  | 选项                                 | 代价        | 技术后果                               |
| ---- | ---------------------------------- | --------- | ---------------------------------- |
| 图标   | 图标库（Lucide / Heroicons）/ 设计定制 / 混合 | 定制贵、风格要统一 | 按需引入控体积；定制要管 SVG                   |
| 字体   | 系统字体 / 开源字体 / 商业字体                 | 商业字体贵且要授权 | Web font 有加载成本，要子集化、要 font-display |
| 字体加载 | 全部加载 / 子集化 / 系统字体栈                 | 子集化要工具    | 影响首屏 LCP                           |

判断心法：图标优先用风格统一的图标库，别东拼西凑。字体优先系统字体栈（零加载成本），要品牌感再上 Web font 并做子集化。版权是红线，商业字体没授权不能用。

## 表四：交互模式（以列表为例）📜

同一个需求，交互模式不同，前后端代价差很多。

| 交互模式          | 适合什么      | 技术后果   | 后端影响         |
| ------------- | --------- | ------ | ------------ |
| 传统分页          | 数据多、要精确跳转 | 简单     | offset 分页    |
| 无限滚动          | 信息流、移动端   | 中等     | 游标分页（cursor） |
| 加载更多按钮        | 折中        | 简单     | 游标分页         |
| 虚拟列表          | 超长列表      | 复杂     | 数据要能分片       |
| 卡片 vs 表格      | 移动 vs 桌面  | 影响布局   | 字段要不要精简      |
| 时间轴 / 日历 / 列表 | 时间型数据     | 复杂度差很大 | 时间查询方式不同     |

判断心法：交互模式决定分页方式，分页方式决定后端接口。**无限滚动必须用游标分页**（offset 在数据变动时会重复或漏数据），这点后端很容易忽略。

## 表五：响应式断点策略 📱

| 策略     | 适合什么        | 代价          |
| ------ | ----------- | ----------- |
| 移动优先   | C 端、主流量手机   | 桌面端要「放大」设计  |
| 桌面优先   | B 端后台、主流量桌面 | 移动端要「重排」    |
| 内容驱动断点 | 追求极致体验      | 要逐页测        |
| 设备驱动断点 | 快速上手        | 平板 / 折叠屏容易崩 |

判断心法：看主流量在哪。C 端默认移动优先，B 端后台默认桌面优先，但都要保证「另一种设备能正常用，不要求极致」。

## 表六：动效与过渡 ✨

| 选项                   | 适合什么     | 代价       | 技术后果 |
| -------------------- | -------- | -------- | ---- |
| 无动效                  | 工具型、后台   | 体验略生硬    | 零成本  |
| CSS 过渡               | 90% 场景   | 简单       | 性能好  |
| 动效库（Framer Motion 等） | 复杂交互、C 端 | 包体积、学习成本 | 要控性能 |
| 原生动画（Lottie 等）       | 品牌动效     | 资源大      | 要懒加载 |

判断心法：动效是调味料，不是主菜。工具型产品能少则少；C 端关键路径（比如支付成功）可以用，但要控性能。动效过度是性能杀手，尤其移动端。
