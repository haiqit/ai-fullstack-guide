# 产品岗的知识内核：六个模块

产品的领域知识看着很散，其实可以归成六块。每一块我都标一句「后端为什么必须懂」，这才是这一节存在的意思。

## 模块一：需求与优先级——决定「先做什么」

**知识内核**

需求的来源就那几种：用户反馈、数据、竞品、老板、销售。同样一条需求，换个来源可信度天差地别。销售提的需求，往往就是一个大客户的特殊要求，拿它当普适需求去排期，很容易翻车。

优先级模型常用的有三个，适用边界完全不一样：

* **RICE**（Reach 触达 × Impact 影响 × Confidence 信心 ÷ Effort 成本）：适合需求多、手里有数据、需要排序的场景。B 端产品常用这个。
* **MoSCoW**（Must / Should / Could / Won't）：适合要谈范围的场景，比如外包、一期上线。
* **Kano**（基本型 / 期望型 / 兴奋型 / 无差异）：适合判断「这个功能到底值不值得做」，尤其是 C 端体验类的需求。

还有一个 MVP 切分。关键是把「能演示」和「能上线」分开。能演示，主流程跑通就行；能上线，还得过异常处理、权限、支付、合规、客服话术、数据埋点这几关。大多数人严重低估「能演示」到「能上线」的距离，实际通常是 2–3 倍工作量。

**后端为什么必须懂**

优先级直接决定数据模型要不要「预留」。一个功能这期不做、下期做，如果模型里没留字段或状态，下期就是一次迁移。RICE 算出来的「下期」，后端就该提前问一句：下期做的话，这期模型要不要留口子？

MVP 切分同理。产品说「一期先不做退款」，后端就得问：那订单状态要不要预留「已退款」？不预留，二期加退款就得改状态机。这一问，就是全栈的价值。

## 模块二：用户故事与验收条件——决定「做到什么算完成」

**知识内核**

用户故事的格式是：作为【角色】，我想要【功能】，以便【价值】。这个格式的价值不在句式本身，而在于它逼你说清楚「谁」和「为什么」。

**验收条件（Acceptance Criteria）**：一个故事必须能写出可验证的完成标准。写不出来，说明需求压根没想清楚。

**异常态定义**：这是产品最常漏、技术最常踩的地方。一个功能有五种态：正常态、空态、加载态、错误态、边界态（超长、无权限、已满、重复提交）。产品通常只写正常态，剩下四种全甩给技术和设计，结果就是「做出来和想的不一样」。

**后端为什么必须懂**

验收条件就是你的接口契约。产品写「用户可以取消预约」，后端至少要问清楚：

* 取消后钱退不退？全退还是按规则退？
* 取消后时段要不要释放？立即释放还是延迟？
* 有没有时限？开始前 24 小时能取消，之后不能？
* 重复取消怎么办？幂等吗？
* 取消后通知谁？客户、店主、员工？

这些不写清楚，接口根本没法定。产品写验收条件的能力，直接决定后端返工几次。

## 模块三：业务流程与状态机——决定「数据怎么流转」

**知识内核**

只要是活过一段时间的对象（订单、任务、审批、工单、订阅），先画状态图，再画页面。状态图要写清四件事：有哪些状态、哪些转换合法、哪些转换需要条件、哪些转换不可逆。

要有状态机思维：状态不是一个字段，是一组合法转换。产品最常见的错误，是把状态当标签用——「已取消」「已退款」「已完成」随便打，数据自然就对不上了。

还有中间态。很多业务有「占位中」「支付中」「审核中」这种短暂的状态。产品不定义，前端就会出现幽灵订单，后端就会出现对账不平。

**后端为什么必须懂**

状态机是你最熟的思维。迁移到产品上，你能做一件产品往往做不到的事：把业务流程翻译成状态机，再翻译成数据模型。

产品说「订单有已创建、已支付、已取消、已完成」，你可以一层层追问：

* 已创建能直接到已完成吗？（不能，得先支付）
* 已支付能直接到已取消吗？（能，但要走退款。退款算另一个状态，还是就在已取消里？）
* 已取消能回到已创建吗？（不能，不可逆）
* 「支付中」这个中间态到底有没有？有的话持续多久？超时怎么办？

问完这一圈，状态机就干净了，数据模型也稳了。

## 模块四：B 端与 C 端的决策差异——决定「优化什么」

**知识内核**

B 端和 C 端的产品逻辑基本是反着来的，混着套必翻车。

| 维度    | B 端        | C 端        |
| ----- | ---------- | ---------- |
| 核心目标  | 效率、准确、可管控  | 转化、留存、体验   |
| 用户耐心  | 高（是工作，愿意学） | 低（随时会走）    |
| 功能密度  | 高（一页塞很多）   | 低（一屏一件事）   |
| 权限复杂度 | 高（角色、数据范围） | 低（本人即可）    |
| 异常处理  | 要详细（要能追责）  | 要友好（别吓跑用户） |
| 迭代方式  | 按客户、按合同    | 按版本、按数据    |
| 决策者   | 老板、管理员     | 用户本人       |

**后端为什么必须懂**

因为 B 端和 C 端的后端架构根本不一样。

* **B 端重权限和数据隔离**：多租户、角色、数据范围。接口设计头一个要考虑的就是「谁能看谁的数据」。
* **C 端重并发和体验**：缓存、CDN、限流、防刷。接口设计要考虑的是「量大不大、会不会被恶意请求、要不要扛秒杀」。

一个产品如果 B 端 C 端都做（比如 SaaS 有店主端和客户端），后端还得自己判断：这两端的接口该不该共用、数据模型该不该共用、权限该不该共用。这个判断产品给不了，只有两头都懂的后端能给。

## 模块五：商业化三件套——决定「技术怎么支撑收费」

**知识内核**

只要要收钱，就绕不开三个决策。而且这三个决策，直接决定后端架构长什么样。

**计费模型**：按量（用多少收多少）、按席位（多少人收多少）、按功能（开哪个模块收多少）、按订阅周期（月/年）。混合计费很常见，比如基础订阅 + 超量按量。

**免费版策略**：免费版给什么、限什么。限制维度常见的有：功能数、用量（单量/存储/调用次数）、席位数、时长。重点是——限制维度必须是能实时计量的，否则技术根本做不出来。

**数据隔离方式**：独立库、独立 schema，还是共享表加 tenant\_id。这个后面后端章细讲，但产品阶段就得定，因为它直接影响定价——独立库成本高，定价得能覆盖。

**后端为什么必须懂**

这三个决策，每一个都是后端的硬约束。

* 计费模型决定你要不要做计量系统（用量采集、聚合、出账）。
* 免费版限制决定你要不要做配额系统（实时计数、跨周期重置、超限拦截）。
* 数据隔离决定你的库表设计和查询模式（每个查询都得带 tenant\_id）。

产品不懂技术，就会提出「免费版每月限 10 单，但退款不算」这种需求。听着简单，技术上要处理：跨月边界怎么算、退款怎么扣回、时区按谁的、计数存哪、并发下单会不会超额。这些细节产品不定义，后端就得猜，猜错就返工。

## 模块六：合规与风险底线——决定「什么不能做」

**知识内核**

合规不是法务的事，是产品阶段就要定的约束。因为它是不可逆的。

* **隐私与数据**：收集什么数据、存多久、能不能跨境、用户能不能要求删除（被遗忘权）。隐私政策不是上线前贴个链接就完事，产品设计时就得知道哪些字段必须收集、哪些能不收。
* **支付资质**：自己收钱得有支付牌照，或者接持牌通道。分账、二清是红线。
* **内容与资质**：有些行业（医疗、教育、金融）有前置审批。
* **数据留存**：有些行业要求日志和交易记录留存 N 年。

**后端为什么必须懂**

合规约束属于不可逆决策。数据模型定了、数据存下去了，再改合规要求，可能要停机迁移，严重的得删库重来。

产品不懂这条，后期就会提「我们加个删除账号功能」。后端一看：数据散在十几张表，还有日志和备份，根本删不干净。这就是产品阶段没定「数据生命周期」的代价。
