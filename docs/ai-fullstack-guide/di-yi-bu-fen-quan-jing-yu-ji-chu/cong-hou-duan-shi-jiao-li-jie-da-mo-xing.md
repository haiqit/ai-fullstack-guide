# 从后端视角理解大模型

## 把模型当成一个「有特殊约束的依赖」

如果你写过后端服务，可以这样理解模型：它是一个**远程依赖**，只不过它有几个不太常见的约束。

| 普通远程依赖   | 大模型            |
| -------- | -------------- |
| 输出是确定的   | 输出是概率性的        |
| 延迟通常在毫秒级 | 延迟从几百毫秒到几十秒    |
| 成本按调用次数算 | 成本按 token 数量算  |
| 契约稳定     | 契约随模型版本变化      |
| 超时重试即可   | 重试可能带来不一致的语义结果 |

把这几条记牢，很多设计决策就自然了：

* 因为输出是概率性的，所以要**缓存**、要**评测**，而不是只看一次结果。
* 因为延迟高且波动大，所以要**流式输出**、要**超时与降级**。
* 因为成本按 token 算，所以要**控制上下文长度**，而不是无脑塞满。
* 因为契约会变，所以要把**模型接入抽象成一层**，而不是散落在业务代码里。

## Go 类比

在 Go 里接口定义清晰，换个实现只改一处。模型接入层也应该如此：业务代码依赖的不是某个厂商 SDK，而是一个你定义的接口，比如：

```go
// 业务只依赖这个接口，不依赖具体厂商
type ChatModel interface {
    Chat(ctx context.Context, req ChatRequest) (ChatResponse, error)
}
```

Python 侧对应的是类型协议（`Protocol` / 抽象基类），或者基于 `AsyncOpenAI` 之类的客户端包一层适配器。关键不是语法，而是**依赖倒置**这条原则在 AI 领域同样成立。

## 小结

模型的不可控性不是需要「克服」的缺陷，而是要**在设计时就承认的前置条件**。承认它，架构就会自然长得和普通后端服务一样：有边界、有降级、有观测。
