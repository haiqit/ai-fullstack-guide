# 推理服务的形态与选型

## 三种常见形态

| 形态     | 代表         | 优点        | 代价              |
| ------ | ---------- | --------- | --------------- |
| 托管 API | 云厂商 / 模型厂商 | 零运维、弹性好   | 单价高、数据出域        |
| 自托管推理  | vLLM、TGI 等 | 成本可控、数据可控 | 需要 GPU 运维、扩缩容麻烦 |
| 混合路由   | 两者结合       | 兼顾成本与弹性   | 架构复杂、需要统一接入层    |

## 选型先问四个问题

1. **数据能不能出域？** 不能出域，基本只能自托管或专有部署。
2. **峰值并发是多少？** 自托管的容量是按 GPU 规划的，弹性远不如托管 API。
3. **延迟预算是多少？** 首 token 延迟和总生成时间要分开看。
4. **成本模型是什么？** 按 QPS 稳定负载算，自托管通常更便宜；突发流量则托管更省心。

## 一个务实的路径

先用托管 API 验证需求，把接入层抽象好；等流量和成本都可预测了，再把一部分负载迁到自托管。

反过来做——一开始就自建推理集群——通常会把团队拖进 GPU 运维，而产品方向还没验证。
